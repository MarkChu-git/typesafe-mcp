# `where` 支持"满足任意一条"

2026-10-14，Sonnet（claude-sonnet-5-5），Claude Code 2.1.294，每次运行最多 20 轮。server instructions 用当前发布的 V6。标准答案还没经过人工复核，所以这里的得分只用来比较改动前后。

## 问题

[写代码时的调用意愿](2026-10-14-coding-moments.md)里发现：按多条规则审代码时，agent 每条规则问一个是非题，想要的是"违反任意一条"的文件，`where` 却要所有条件都满足才算匹配。12 次用了 Jev 的 change-review 运行里，大约 7 次在这里出错，之后要么再问一次，要么再读一轮。

## 改了什么

- `where` 里可以写 `$or`：一组条件对象，记录满足其中一个就算匹配，比如 `{"$or": [{"r1": true}, {"r2": true}]}`。`$or` 旁边的其他条件仍然都要满足。
- `where` 的说明加了一句：被筛掉的记录，答案和 `unsure` 里的原文都不会返回，几十条以内就别筛了。
- 工具定义里 `where` 仍然显示成普通对象。`jev_ask` 的定义从 4,232 字符变成 4,396 字符，每次模型调用大约多读 41 token。

## 怎么测

用 `jev-code-rule` 和 `jev-code-deferred-rule` 两组。这两组的系统提示里有一条用户规则，让 agent 先问 Jev 再自己读，几乎每次都会用上 `where`，正好用来看这次改动。旧代码和新代码各跑一遍：change-review 每组 4 次，其他任务每组 2 次。

## 结果

change-review：

| | 改之前 | 改之后 |
| --- | --- | --- |
| 平均 token，延迟加载 | 87k | 57k（−34%） |
| 平均 token，一开始加载 | 84k | 75k（−11%） |
| 平均轮数 | 8.9 | 6.8 |
| 每次运行调用 Jev 的次数 | 2.25 | 1 |
| `where` 写错 | 8 次里 6 次 | 0 次 |

得分都是 1.00。延迟加载组 4 次里有 3 次直接写了 `{"$or": [{"r1": true}, …, {"r6": true}]}`，拿到结果后一个文件都没再开，每次约 49k，比 agent 自己读文件的 52k 还少。一开始加载组 4 次里有 3 次没用 `where`，照说明拿回了全部答案；剩下一次把"违规"和"没把握"都写进了 `$or`。

其他任务：

| 任务 | 改之前（延迟加载 / 一开始加载） | 改之后 |
| --- | --- | --- |
| bug-files | 78k / 70k | 76k / 74k |
| ci-failures | 52k / 61k | 51k / 60k |
| incident-logs | 88k，0.98 分 / 没用 Jev | 87k，0.96 分 / 没用 Jev |

差别都在正常波动范围内。incident-logs 的延迟加载组两次都把"卡住的结账请求"和"原因"合进一次 `$or` 调用，原来要问两次，但之后仍然用 grep 核对，token 没有省下来。对照任务 rename-callers 两组都没有误用。

## 结论

`$or` 和"几十条以内别筛"这两处，省掉了 change-review 上筛选写错多出来的那一轮。延迟加载时，用 Jev 审代码的开销降到了比自己读还低。其他任务不受影响。

## 复现

改之后在本分支跑：

```bash
bun run eval --tasks change-review --arms jev-code-deferred-rule,jev-code-rule --reps 4 --max-turns 20 --allow-unreviewed
bun run eval --tasks bug-files,ci-failures,incident-logs,rename-callers --arms jev-code-deferred-rule,jev-code-rule --reps 2 --max-turns 20 --allow-unreviewed
```

改之前在改动前一个提交上跑同样的组和任务。change-review 每组的 4 次分两批：一批是[写代码时的调用意愿](2026-10-14-coding-moments.md)里那 2 次，另一批是补跑的 2 次。
